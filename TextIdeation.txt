For your Junior–Mid VFX Software/Pipeline Developer portfolio, I recommend building the Package Dependency Validator version, not the larger Render/Provenance system.

It gives you a better 68-hour project while still demonstrating strong engineering skills.

Recommended Project
VFX Dependency Guardian — Package Dependency Validation System

The tool answers one practical production question:

"Is this published asset/package using the correct, approved versions of all its dependencies?"

Core workflow
Published Package
       ↓
Read Package JSON
       ↓
Discover Dependencies
       ↓
Read Master Version Registry
       ↓
Compare Versions + Status
       ↓
Validate
       ↓
┌──────────┬──────────┬──────────┬──────────┐
│   OK     │ OUTDATED │ MISSING  │ INVALID  │
└──────────┴──────────┴──────────┴──────────┘
       ↓
Detailed Validation Report
       ↓
Optional User-Confirmed Update
Example
character_A

model    v002 → v008    OUTDATED
rig      v001 → v004    OUTDATED
texture  v005           OK
groom    missing        MISSING

Validation: FAILED

The tool should tell the artist/TD exactly what is wrong and what version is expected.

What I'd build
1. Package JSON

Stores what the package currently references.

{
    "asset": "character_A",
    "components": {
        "model": "v002",
        "rig": "v001",
        "texture": "v005",
        "groom": "v001"
    }
}
2. Master Registry

Your source of approved truth.

{
    "character_A": {
        "model": {
            "version": "v008",
            "status": "APPROVED"
        },
        "rig": {
            "version": "v004",
            "status": "APPROVED"
        },
        "texture": {
            "version": "v005",
            "status": "APPROVED"
        },
        "groom": {
            "version": "v002",
            "status": "WIP"
        }
    }
}
3. Validator

This is the heart of the project.

It determines:

MATCH       → OK
OLDER       → OUTDATED
MISSING     → MISSING
BROKEN      → INVALID
DEPRECATED  → INVALID
WIP         → INVALID / WARNING
FUTURE      → INVALID
4. Update mechanism

Don't make automatic "Update All" the default.

Instead:

guardian check character_A

shows:

OUTDATED COMPONENTS

model   v002 → v008
rig     v001 → v004

Then:

guardian update character_A

updates the package only after explicit confirmation.

This demonstrates that you understand production safety.

Why I recommend this over the original idea

Your original concept was:

Dependency Validation
+
Locking
+
Manifest
+
Render
+
Provenance

That's a larger pipeline system.

Your refined concept is:

Dependency Discovery
+
Version Resolution
+
Validation
+
Reporting
+
Controlled Update

This is much more achievable in ~68 hours, while still allowing you to demonstrate serious engineering.

And there's a natural Phase 2:

PHASE 1
Package Dependency Validator
        ↓
PHASE 2
Dependency Locking / Immutable Manifest
        ↓
PHASE 3
Render Provenance
        ↓
PHASE 4
DCC / Farm Integration

You can therefore say in your interview:

"I deliberately scoped the first version around dependency validation and version consistency. I designed the core so that dependency locking and render provenance could be added later without changing the validation engine."

That's a much stronger engineering story than trying to build everything and ending up with half-working features.
